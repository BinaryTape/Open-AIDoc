## 实用演进原则 {id="principles-of-pragmatic-evolution"}

> _语言设计虽然刻于磐石，_
>
> _但这块磐石相当柔软，_
>
> _只要付出一些努力，我们日后仍能重塑其形。_
>                        
> _Kotlin 设计团队_

Kotlin 旨在成为程序员的实用工具。谈及语言演进，其实用本质体现在以下原则中：

*   保持语言与时俱进。
*   保持与用户的持续反馈循环。
*   让用户更新到新版本轻松且舒适。

由于这是理解 Kotlin 如何向前推进的关键，让我们详细展开这些原则。

**保持语言现代**。我们认识到系统会随着时间推移积累旧版内容。曾经的前沿技术在今天可能变得不可救药地过时。我们必须演进语言，使其契合用户的需求并紧跟他们的期望。这不仅包括添加新功能，还包括逐步淘汰那些不再推荐用于生产环境且已成为旧版遗留的功能。

**舒适更新**。诸如从语言中移除内容等不兼容更改，如果处理不当，可能会导致从一个版本迁移到下一个版本时经历痛苦的过程。我们始终会提前很久公布此类更改，将内容标记为已弃用，并在_更改发生之前_提供自动化迁移工具。当语言发生更改时，我们希望全球的大多数代码都已完成更新，从而能够毫无问题地迁移到新版本。

**反馈循环**。经历弃用周期需要付出巨大的努力，因此我们希望尽量减少未来进行的不兼容更改数量。除了依靠我们自身的严谨判断之外，我们相信在实际场景中试用是验证设计的最佳途径。在将其刻石定案之前，我们希望它们经过实战检验。这就是为什么我们抓住一切机会，在语言的生产版本中以某种_预稳定_状态提供我们设计的早期版本：[Experimental、Alpha 或 Beta](components-stability.md)。这些功能尚不稳定；它们随时可能发生更改，而选择使用它们的用户是通过显式选择加入的方式，来表明他们已准备好应对未来的迁移问题。这些用户提供了极其宝贵的反馈，我们收集这些反馈来对设计进行迭代，使其变得坚如磐石。

## 不兼容更改 {id="incompatible-changes"}

如果从一个版本更新到另一个版本时，某些原本可以正常工作的代码不再工作，那么这就是语言中的_不兼容更改_（有时称为“破坏性更改”）。在某些情况下，关于“不再工作”的具体含义可能存在争议，但它绝对包括以下几种情况：

* 原本可以正常编译并运行的代码现在因错误而被拒绝（在编译时或链接时）。这包括移除语言构造以及添加新的限制。
* 原本正常执行的代码现在会抛出异常。

属于“灰色地带”的较不明显情况包括以不同方式处理边缘情况、抛出与之前不同类型的异常、更改仅通过反射可见的行为、修改未记录或未定义行为、重命名二进制构件等。有时此类更改至关重要并会极大地影响迁移体验；有时它们则微不足道。

明确不属于不兼容更改的示例包括：

*   添加新的警告。
*   启用新的语言构造或放宽对现有语言构造的限制。
*   更改私有/内部 API 以及其他实现细节。

“保持语言现代”和“舒适更新”的原则表明，不兼容更改有时是必要的，但必须谨慎引入。我们的目标是让用户提前知晓即将到来的更改，以便他们能够轻松自如地迁移代码。

理想情况下，每项不兼容更改都应通过在有问题的代码中报告的编译时警告（通常称为_弃用警告_）来公布，并附带自动化迁移辅助工具。因此，理想的迁移工作流程如下：

*   更新到版本 A（公布更改的版本）
    *   看到关于即将到来的更改的警告
    *   在工具的帮助下迁移代码
*   更新到版本 B（发生更改的版本）
    *   完全没有遇到任何问题

在实践中，某些更改无法在编译时准确检测到，因此无法报告警告，但至少会通过版本 A 的发布说明通知用户更改将在版本 B 中发生。

### 处理编译器错误 {id="dealing-with-compiler-bugs"}

编译器是复杂的软件，尽管开发者付出了最大努力，但它们仍然存在错误。那些导致编译器自身崩溃、报告虚假错误或生成明显失败代码的错误，虽然令人恼火且往往令人难堪，但很容易修复，因为这些修复不构成不兼容更改。其他错误可能会导致编译器生成不会报错的错误代码：例如，遗漏了源代码中的某些错误或仅仅生成了错误的指令。对此类错误的修复在技术上属于不兼容更改（某些代码曾经可以正常编译，但现在不再能够编译），但我们倾向于尽快修复它们，以防止不良的代码模式在用户代码中蔓延。在我们看来，这支持了“舒适更新”原则，因为这样遇到该问题的用户会更少。当然，这仅适用于在发布版本中出现后不久就被发现的错误。

## 决策制定 {id="decision-making"}

Kotlin 的最初创建者 [JetBrains](https://jetbrains.com) 在社区的帮助下，并与 [Kotlin Foundation](https://kotlinfoundation.org/) 合作推动其发展。

Kotlin 编程语言的所有更改均由[首席语言设计师](https://kotlinfoundation.org/structure/)（目前是 Michail Zarečenskij）统筹监督。首席设计师对与语言演进相关的所有事务拥有最终决定权。此外，对完全稳定组件的不兼容更改必须获得指定于 [Kotlin Foundation](https://kotlinfoundation.org/structure/) 下的[语言委员会](https://kotlinfoundation.org/structure/)（目前由 Jeffrey van Gogh、Werner Dietl 和 Michail Zarečenskij 组成）的批准。

语言委员会就将要进行哪些不兼容更改以及应采取哪些确切措施使用户更新尽可能无缝做出最终决定。在此过程中，它依赖于一套[语言委员会准则](https://kotlinfoundation.org/language-committee-guidelines/)。

## 语言功能交付 {id="language-feature-delivery"}

正如 [Kotlin 发布流程](releases.md)中所述，语言功能在_语言版本_（2._x_._0_）或其随后的_工具版本_（2._x_._20_）中交付。

我们努力保持语言版本和工具版本之间的相互兼容，因此对编译器的更改主要是优化以及警告的添加/移除。预稳定功能可以随时添加、移除或更改。

语言版本通常会添加新功能，将预稳定功能晋升为稳定版，并可能会移除或更改之前已弃用的功能。

### EAP 构建 {id="eap-builds"}

在发布语言和工具版本的稳定版本之前，我们会发布一些被称为 _EAP_（即“Early Access Preview”，抢先体验预览）的预览构建，使我们能够更快地迭代并从社区收集反馈。语言版本的 EAP 通常会生成稍后会被稳定版编译器拒绝的二进制文件，以确保二进制格式中可能存在的错误不会存留超过预览期。最终的候选发布版，例如 RC2 或 RC3，通常不受此限制。有关更多信息，请参阅[参与 Kotlin 抢先体验预览](eap.md)。

### 预稳定功能 {id="pre-stable-features"}

根据上述的反馈循环原则，我们公开迭代我们的设计，并发布其中某些功能处于_预稳定_状态且_预期会发生更改_的语言版本。此类功能可以在任何时间点被添加、更改或移除，且无需预先警告。我们尽最大努力确保不知情的使用者不会意外使用预稳定功能。此类功能通常需要在代码中或在项目配置中进行某种显式的选择加入。

Kotlin 语言功能可以具有以下状态之一：

* **探索与设计**。我们正在考虑向语言引入新功能。这涉及讨论它将如何与现有功能集成、收集用例以及评估其潜在影响。我们需要用户就该功能将解决的问题以及它所适用的用例提供反馈。只要有可能，我们还会尝试预估这些用例和问题发生的频率。通常，这些想法会被记录为 YouTrack 问题，并在那里继续展开讨论。

* **KEEP 讨论**。我们基本确定该功能应该添加到语言中。我们的目标是在名为 _Kotlin Evolution and Enhancement Process_（KEEP）的文档中提供动机、用例、设计以及其他重要细节。我们期望用户的反馈集中在讨论 KEEP 中提供的所有信息上。

* **预览中**。功能原型已准备就绪，你可以使用特定于功能的编译器选项来启用它。我们寻求关于你对该功能的使用体验的反馈，包括它与你的代码库集成的难易程度、它如何与现有代码交互，以及任何 IDE 支持问题或建议。根据反馈，该功能的设计可能会发生重大更改，或者可能被完全撤销。当功能处于_预览中_时，它具有 Experimental 或 Beta [稳定性级别](components-stability.md#stability-levels-explained)。

* **稳定**。该语言功能现在已成为 Kotlin 语言的一等公民。我们保证其向后兼容性，并将提供工具支持。

* **已撤销**。我们已撤销该提案，并且不会在 Kotlin 语言中实现该功能。如果处于_预览中_的功能不适合 Kotlin，我们可能会将其撤销。

[查看 Kotlin 语言提案及其状态的完整列表](kotlin-language-features-and-proposals.md)。

## 库 {id="libraries"}

没有生态系统，语言就无从谈起，因此我们格外重视确保库的平稳演进。

理想情况下，新版本的库可以用作旧版本的“直接替代品 (drop-in replacement)”。这意味着即使未重新编译应用程序，升级二进制依赖项也不会破坏任何内容（这在动态链接下是可能的）。

一方面，为了实现这一点，编译器必须在独立编译的约束下提供某些_应用程序二进制接口_（ABI）稳定性保证。这就是为什么语言中的每项更改都会从二进制兼容性角度进行审查的原因。

另一方面，很大程度上取决于库作者对哪些更改是安全的保持谨慎。因此，库作者必须理解源代码更改如何影响兼容性，并遵循特定的最佳做法来保持其库的 API 和 ABI 稳定。从库演进的角度考虑语言更改时，我们做出了以下假设：

* 库代码应始终显式指定 public/protected 函数和属性的返回值类型，绝不在公共 API 中依赖类型推断。类型推断中的细微更改可能会导致返回值类型无意中发生变化，从而引发二进制兼容性问题。
* 由同一库提供的重载函数和属性在本质上应执行相同的操作。类型推断的更改可能会导致在调用站点获知更精确的静态类型，从而导致重载解析发生变化。

库作者可以使用 `@Deprecated` 和 [`@RequiresOptIn`](opt-in-requirements.md) 注解来控制其 API 暴露面的演进。请注意，`@Deprecated(level=HIDDEN)` 可用于即使对已从 API 中移除的声明也能保留二进制兼容性。

此外，按照惯例，名为“internal”的软件包不被视为公共 API。驻留在名为“experimental”的软件包中的所有 API 均被视为预稳定状态，随时可能发生更改。

我们根据上述原则演进针对稳定平台的 Kotlin 标准库（`kotlin-stdlib`）。对其 API 契约的更改与语言本身的更改遵循相同的流程。

## 编译器选项 {id="compiler-options"}

编译器接受的命令行选项也是一种公共 API，并且遵循相同的考量。受支持的选项（那些没有 "-X" 或 "-XX" 前缀的选项）只能在语言版本中添加，并且在移除之前应妥善弃用。"-X" 和 "-XX" 选项是实验性的，可以随时添加和移除。

## 兼容性工具 {id="compatibility-tools"}

随着旧版功能的移除和错误的修复，源语言会发生变化，未正确迁移的旧代码可能不再能够编译。正常的弃用周期为迁移提供了充裕的时间，即使该周期结束并且更改已在稳定版本中交付，仍然有办法编译未迁移的代码。

### 兼容性选项 {id="compatibility-options"}

我们提供了兼容性选项，使新的 Kotlin 版本能够模拟旧版本的行为：

* `-language-version X.Y` – Kotlin 语言版本 X.Y 的兼容模式。当你的代码使用在更高版本中引入的语言功能时，编译器会报告错误。
* `-api-version X.Y` – Kotlin API 版本 X.Y 的兼容模式。编译器会忽略使用了更高版本中引入的 Kotlin 标准库 API 的声明，包括编译器生成的代码所引用的 API。

为了给你更多时间进行迁移，在 JVM 上，除了最新的稳定版本外，我们还支持至少前三个语言和 API 版本。这让库作者可以采用较新的编译器版本，同时保持与使用旧编译器版本的使用者兼容。在其他平台上，你也可以配置较旧的语言和 API 版本，但与 JVM 不同的是，使用者仍然需要使用最新的编译器版本。

在大多数项目中，请将这两个选项设置为相同的版本。较低的 API 版本主要在需要与较旧版本的 Kotlin 标准库保持兼容时有用。

积极维护的代码库可以受益于尽快获得错误修复，而无需等待完整的弃用周期结束。这些项目可以启用 [`-progressive` 选项](compiler-reference.md#progressive)，以便在工具版本成为默认版本之前就采用这些更改。

你可以在[命令行](compiler-reference.md#common-options)上，或者使用 [Gradle](gradle-compiler-options.md#common-attributes) 或 [Maven](maven-kotlin-compiler.md#specify-compiler-options) 构建工具来配置这些选项。

### 演进二进制格式 {id="evolving-the-binary-format"}

与在最坏情况下可以通过手动修复的源代码不同，二进制文件迁移起来要困难得多，这使得向后兼容性在二进制文件的情况下至关重要。二进制文件的不兼容更改会让更新变得非常不适，因此引入时应该比源语言语法的更改更加谨慎。

对于编译器的完全稳定版本，默认的二进制兼容性协议如下：

* 所有二进制文件都是向后兼容的；这意味着较新的编译器可以读取较旧的二进制文件（例如，1.3 可以理解 1.0 到 1.2）。
* 较旧的编译器会拒绝依赖新功能的二进制文件（例如，1.0 编译器会拒绝使用协程的二进制文件）。
* 尽可能（但我们无法保证）使二进制格式在很大程度上与下一个语言版本保持向前兼容，但不兼容更晚的版本（在未使用新功能的情况下，例如，1.9 可以理解来自 2.0 的大部分二进制文件，但无法理解 2.1 的）。

该协议专为舒适更新而设计，因为即使某个项目使用的是稍微过时的编译器，也不会因此被阻止更新其依赖项。

请注意，并非所有目标平台都达到了这一稳定水平，但 Kotlin/JVM 已经达到了。

#### Kotlin klib 二进制文件 {id="kotlin-klib-binaries"}

Kotlin klib 二进制文件在 Kotlin 1.9.20 中已达到[稳定 (Stable)](components-stability.md#stability-levels-explained)级别。但是，你需要牢记一些兼容性细节：

* 从 Kotlin 1.9.20 开始，klib 二进制文件向后兼容。例如，2.0.x 编译器可以读取由 1.9.2x 编译器生成的二进制文件。
* _不_保证向前兼容。例如，2.0.x 编译器_不_保证能够读取由 2.1.x 编译器生成的二进制文件。

> Kotlin cinterop klib 二进制文件仍处于 [Beta](components-stability.md#stability-levels-explained) 阶段。
> 目前，我们无法对不同 Kotlin 版本之间的 cinterop klib 二进制文件提供具体的兼容性保证。
