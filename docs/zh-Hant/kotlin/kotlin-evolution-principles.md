## 務實演進原則 {id="principles-of-pragmatic-evolution"}

> _語言設計並非一成不變，_
>
> _這塊基石其實相當柔軟，_
>
> _只要稍加努力，我們日後便能重塑其形。_
>                        
> _Kotlin 設計團隊_

Kotlin 旨在成為程式設計師的務實工具。在語言演進方面，其務實的本質體現於以下原則：

*   讓語言隨著時間推移保持現代化。
*   與使用者保持持續的回饋循環。
*   讓使用者能輕鬆舒適地更新至新版本。

這是理解 Kotlin 如何向前發展的關鍵，讓我們深入探討這些原則。

**保持語言現代化**。我們深知系統會隨著時間積累舊版包袱。曾經尖端的技術在今天可能會變得無可救藥地過時。我們必須推動語言的演進，以滿足使用者的需求並符合他們的期望。這不僅包括新增特性，還包括逐步淘汰那些不再推薦用於正式環境且已過時的舊功能。

**舒適的更新體驗**。如果處理不當，諸如從語言中移除某些功能等不相容的變更，可能會導致從一個版本遷移到下一個版本時痛苦不堪。我們一定會提前充分宣布此類變更，將相關項目標記為棄用，並在_變更發生之前_提供自動化移轉工具。當語言發生變更時，我們希望世界上大多數程式碼都已經完成更新，從而順利遷移到新版本，不會遇到問題。

**回饋循環**。經歷棄用週期需要付出大量心力，因此我們希望盡可能減少未來可能出現的不相容變更數量。除了運用我們最專業的判斷外，我們相信在現實世界中嘗試是驗證設計的最佳途徑。在塵埃落定之前，我們希望它們經歷過實戰檢驗。這就是為什麼我們抓住一切機會，在語言的正式版本中提供設計的早期版本，但會將其歸入某種_前穩定 (pre-stable)_ 狀態：[Experimental、Alpha 或 Beta](components-stability.md)。此類功能並不穩定；它們隨時可能發生變化，選擇使用它們的使用者明確表示他們已準備好應對未來的遷移問題。這些使用者提供了寶貴的回饋意見，我們收集這些意見來反覆疊代設計，使其變得堅若磐石。

## 不相容的變更 {id="incompatible-changes"}

如果在從一個版本更新到另一個版本時，某些過去可以正常運作的程式碼不再適用，這就是語言中的_不相容變更_（有時稱為「破壞性變更 (breaking change)」）。
在某些情況下，對於「不再適用」的具體定義可能存在爭議，但它絕對包括以下情況：

* 原本能正常編譯並執行的程式碼，現在被拒絕並報錯（在編譯或連結時期）。
    這包括移除語言結構以及新增限制。
* 原本正常執行的程式碼，現在拋出例外。

屬於「灰色地帶」的較不明顯情況包括：對邊緣情況的處理方式不同、拋出與以往不同型別的例外、變更僅能透過反射觀察到的行為、修改未記載或未定義的行為、重新命名二進位產物等等。
有時此類變更至關重要，會極大地影響遷移體驗；有時它們無關緊要。

絕對不屬於不相容變更的一些範例包括：

*   新增警告。
*   啟用新的語言結構或放寬現有結構的限制。
*   變更私有／內部 API 以及其他實作細節。

保持語言現代化與舒適更新的原則表明，不相容的變更時常是必要的，但必須審慎引入。我們的目標是讓使用者提前知曉即將到來的變更，使他們能夠輕鬆舒適地遷移程式碼。

理想情況下，每個不相容的變更都應透過有問題程式碼中回報的編譯期警告來宣布（通常稱為_棄用警告_），並輔以自動化遷移工具。
因此，理想的遷移工作流程如下：

*   更新至版本 A（宣布變更的版本）
    *   看到關於即將到來的變更警告
    *   在工具的協助下遷移程式碼
*   更新至版本 B（變更實際發生的版本）
    *   完全不會遇到任何問題

在實務中，某些變更無法在編譯期準確偵測，因此無法回報警告，但至少會透過版本 A 的版本資訊通知使用者，版本 B 即將迎來變更。

### 處理編譯器錯誤 {id="dealing-with-compiler-bugs"}

編譯器是複雜的軟體，儘管開發人員付出了最大努力，但仍難免存在錯誤 (bugs)。
導致編譯器本身故障、回報虛假錯誤或產生明顯有問題之程式碼的錯誤，雖然令人惱火且往往令人尷尬，但很容易修復，因為這些修復並不構成不相容的變更。
其他錯誤可能會導致編譯器產生不正確但不會崩潰的程式碼：
例如，遺漏原始碼中的某些錯誤，或者單純產生了錯誤的指令。
修復此類錯誤在技術上屬於不相容變更（某些程式碼過去可以正常編譯，但現在不行了），但我們傾向於儘快修復它們，以防止不良的程式碼模式在使用者的程式碼中蔓延。
在我們看來，這支持了舒適更新的原則，因為更少的使用者有機會遇到該問題。
當然，這僅適用於在發布版本後不久就發現的錯誤。

## 決策制定 {id="decision-making"}

Kotlin 的最初建立者 [JetBrains](https://jetbrains.com) 正在社群的協助下，並與 [Kotlin Foundation](https://kotlinfoundation.org/) 合作推動其發展。

Kotlin 程式設計語言的所有變更均由[語言首席設計師](https://kotlinfoundation.org/structure/)（目前為 Michail Zarečenskij）監督。
首席設計師對與語言演進相關的所有事務擁有最終決定權。
此外，對完全穩定元件進行的不相容變更必須獲得 [Kotlin Foundation](https://kotlinfoundation.org/structure/) 下指定的[語言委員會](https://kotlinfoundation.org/structure/)批准（目前由 Jeffrey van Gogh、Werner Dietl 和 Michail Zarečenskij 組成）。

語言委員會對將要進行哪些不相容變更，以及應採取哪些具體措施使使用者更新盡可能無縫銜接做出最終決定。
在此過程中，它遵循一系列[語言委員會準則](https://kotlinfoundation.org/language-committee-guidelines/)。

## 語言功能交付 {id="language-feature-delivery"}

如 [Kotlin 發布流程](releases.md)中所述，語言特性會在_語言版本_（2._x_._0_）或其隨後的_工具版本_（2._x_._20_）中推出。

我們盡力保持語言版本和工具版本之間的相容性，因此對編譯器的變更主要限於最佳化以及警告的新增／移除。
前穩定功能可能隨時被新增、移除或修改。

語言版本通常會新增特性、將前穩定功能提升為穩定版，並可能移除或修改先前已棄用的功能。

### EAP 組建 {id="eap-builds"}

在發布語言和工具版本的穩定版之前，我們會發布一些稱為 _EAP_（「Early Access Preview」的縮寫）的預覽組建，這讓我們能夠更快速地疊代並收集社群的回饋。
語言版本的 EAP 通常會產生稍後會被穩定版編譯器拒絕的二進位檔案，以確保二進位格式中可能存在的錯誤不會在預覽期之後繼續留存。
最終的候選版本（例如 RC2 或 RC3）通常不會受到此限制。如需詳細資訊，請參閱[參與 Kotlin Early Access Preview](eap.md)。

### 前穩定功能 {id="pre-stable-features"}

根據上述的回饋循環原則，我們以公開的方式反覆疊代設計，並發布某些功能處於_前穩定_狀態且_預期會改變_的語言版本。
此類功能可以隨時新增、變更或移除，恕不另行通知。
我們會盡最大努力確保前穩定功能不會被不知情的使用者意外使用。
這些功能通常需要在程式碼中或在專案配置中進行某種明確宣告同意 (opt-in)。

Kotlin 語言功能可以具有以下狀態之一：

* **探索與設計**。我們正在考慮在語言中引入新功能。
  這包括討論它將如何與現有功能整合、收集使用案例，並評估其潛在影響。
  我們需要使用者針對此功能將解決的問題及其對應的使用案例提供回饋。
  只要可行，我們也會嘗試評估這些使用案例和問題發生的頻率。
  通常，這些構想會記錄為 YouTrack 問題，並在其中繼續討論。

* **KEEP 討論**。我們相當確定應該將該特性新增至語言中。
  我們旨在名為 _Kotlin Evolution and Enhancement Process_ (KEEP) 的文件中提供動機、使用案例、設計及其他重要細節。
  我們希望使用者的回饋能聚焦於討論 KEEP 中提供的所有資訊。

* **預覽中**。功能原型已就緒，你可以使用特定於該功能的編譯器選項將其啟用。
  我們期待獲取有關你使用該功能體驗的回饋，包括它整合到你的程式碼庫的難易程度、它如何與現有程式碼互動，以及任何 IDE 支援問題或建議。
  根據回饋，該功能的設計可能會發生重大變更，或者可能完全被撤銷。當功能處於_預覽中_時，它具有 Experimental 或 Beta [穩定性級別](components-stability.md#stability-levels-explained)。

* **穩定**。該語言功能現已成為 Kotlin 語言中的一等公民。
  我們保證其向下相容性，並將提供工具支援。

* **已撤銷**。我們已經撤銷該提案，並且不會在 Kotlin 語言中實作該功能。
  如果處於_預覽中_的功能不適合 Kotlin，我們可能會將其撤銷。

[查看 Kotlin 語言提案及其狀態的完整清單](kotlin-language-features-and-proposals.md)。

### 不同元件的狀態 {id="status-of-different-components"}

進一步了解 [Kotlin 中不同元件的穩定性狀態](components-stability.md)，例如 Kotlin/JVM、JS 和 Native 編譯器，以及各種程式庫。

## 程式庫 {id="libraries"}

如果沒有生態系統，語言便毫無意義，因此我們格外注重實現流暢的程式庫演進。

理想情況下，程式庫的新版本可以作為舊版本的「直接替代品 (drop-in replacement)」。
這意味著升級二進位相依性不應破壞任何內容，即使應用程式沒有重新編譯也是如此（這在動態連結下是可行的）。

一方面，為了實現這一目標，編譯器必須在獨立編譯的約束下提供特定的_應用程式二進位介面_ (ABI) 穩定性保證。
這就是為什麼語言中的每一項變更都會從二進位相容性的角度進行審查。

另一方面，很大程度上取決於程式庫作者對於進行哪些安全變更保持謹慎。
因此，程式庫作者必須了解原始碼變更如何影響相容性，並遵循某些最佳實務以保持其程式庫的 API 和 ABI 穩定。
以下是我們從程式庫演進角度考慮語言變更時做出的幾點假設：

* 程式庫程式碼應始終明確指定 public/protected 函式與屬性的傳回型別，絕不要對公開 API 依賴型別推論。型別推論的細微變化可能會導致傳回型別無意中改變，從而引發二進位相容性問題。
* 由同一個程式庫提供的多載函式和屬性在實質上應該執行相同的工作。型別推論的變更可能會導致在呼叫點得知更精確的靜態型別，從而導致多載解析發生改變。

程式庫作者可以使用 `@Deprecated` 和 [`@RequiresOptIn`](opt-in-requirements.md) 註解來控制其 API 外觀的演進。請注意，`@Deprecated(level=HIDDEN)` 可用於保留二進位相容性，即使對於已從 API 中移除的宣告也是如此。

此外，按照慣例，名為「internal」的套件不被視為公開 API。位於名為「experimental」的套件中的所有 API 均被視為前穩定狀態，隨時可能發生變更。

我們根據上述原則演進穩定平台的 Kotlin 標準函式庫 (`kotlin-stdlib`)。其 API 協定的變更與語言本身的變更遵循相同的程序。

## 編譯器選項 {id="compiler-options"}

編譯器接受的命令列選項也是一種公開 API，它們受到相同的考量約束。
受支援的選項（不具有「-X」或「-XX」前綴的選項）只能在語言版本中新增，並且在移除之前應經過適當的棄用程序。「-X」和「-XX」選項屬於實驗性質，隨時可以新增和移除。

## 相容性工具 {id="compatibility-tools"}

隨著舊版功能被移除以及錯誤得到修復，原始碼語言會發生變化，未經適當遷移的舊程式碼可能無法再編譯。
正常的棄用週期為遷移預留了充足的時間，甚至當該週期結束且變更在穩定版本中發布時，仍有辦法編譯未遷移的程式碼。

### 相容性選項 {id="compatibility-options"}

我們提供相容性選項，讓新的 Kotlin 版本能夠模擬舊版本的行為：

* `-language-version X.Y` – Kotlin 語言版本 X.Y 的相容模式。當你的程式碼使用在後續版本中引入的語言特性時，編譯器會回報錯誤。
* `-api-version X.Y` – Kotlin API 版本 X.Y 的相容模式。編譯器會忽略使用在後續版本中引入的 Kotlin 標準函式庫 API 的宣告，包括編譯器產生的程式碼所引用的 API。

為了給你更多時間進行遷移，在 JVM 上，除最新穩定版本外，我們還支援至少三個先前的語言和 API 版本。這讓程式庫作者能夠採用較新的編譯器版本，同時保持與使用較舊編譯器版本的使用者相容。在其他平台上，你也可以配置較舊的語言和 API 版本，但與 JVM 不同的是，使用者仍需要使用最新的編譯器版本。

在大多數專案中，將這兩個選項設定為相同的版本。較低的 API 版本主要適用於你需要保持與舊版本 Kotlin 標準函式庫相容的情況。

積極維護的程式碼庫可以受益於儘早取得錯誤修復，而無需等待整個棄用週期完成。
這些專案可以啟用 [`-progressive` 選項](compiler-reference.md#progressive)，在工具版本中採用這些變更，趁其成為預設值之前先行套用。

你可以在[命令列](compiler-reference.md#common-options)上，或使用 [Gradle](gradle-compiler-options.md#common-attributes) 或 [Maven](maven-kotlin-compiler.md#specify-compiler-options) 建置工具來配置這些選項。

### 演進二進位格式 {id="evolving-the-binary-format"}

與在最壞情況下可以手動修復的原始碼不同，二進位檔案要遷移困難得多，這使得向下相容性在二進位檔案的情況下變得至關重要。
二進位檔案的不相容變更可能會帶來極為不便的更新體驗，因此引入時必須比原始碼語法變更更加謹慎。

對於完全穩定的編譯器版本，預設的二進位相容性協定如下：

* 所有二進位檔案均向下相容；這意味著較新的編譯器可以讀取較舊的二進位檔案（例如，1.3 可以理解 1.0 至 1.2）。
* 較舊的編譯器會拒絕依賴新特性的二進位檔案（例如，1.0 編譯器會拒絕使用協同程式的二進位檔案）。
* 理想情況下（但我們無法保證），二進位格式多半能與下一個語言版本向前相容，但不能與更後續的版本向前相容（在未使用新特性的情況下，例如，1.9 可以理解 2.0 的大部分二進位檔案，但無法理解 2.1 的二進位檔案）。

該協定旨在實現舒適的更新體驗，因為即使專案使用的是稍微過時的編譯器，也不會因更新相依性而受到阻礙。

請注意，並非所有目標平台都達到了此穩定性等級，但 Kotlin/JVM 已經達到。

#### Kotlin klib 二進位檔案 {id="kotlin-klib-binaries"}

Kotlin klib 二進位檔案在 Kotlin 1.9.20 中已達到[穩定 (Stable)](components-stability.md#stability-levels-explained) 級別。
但是，有一些相容性細節需要牢記：

* 自 Kotlin 1.9.20 起，klib 二進位檔案向下相容。例如，2.0.x 編譯器可以讀取由 1.9.2x 編譯器產生的二進位檔案。
* _不_保證向前相容。例如，_不_保證 2.0.x 編譯器可以讀取由 2.1.x 編譯器產生的二進位檔案。

> Kotlin cinterop klib 二進位檔案仍處於 [Beta](components-stability.md#stability-levels-explained) 階段。
> 目前，我們無法為不同 Kotlin 版本之間的 cinterop klib 二進位檔案提供具體的相容性保證。
